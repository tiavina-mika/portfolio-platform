## Overview

There are two kinds of translation: the interface strings of each app (JSON files, one set per app) and the content written by the owner in the back-office (stored in the database under `translated`, see [DOMAIN_MODEL.md](DOMAIN_MODEL.md)).

## Locales

| Locale | Language | Server | Back-office | Website |
|---|---|---|---|---|
| `fr` | French, the default and the reference of the checks | yes | yes | yes (default) |
| `en` | English | yes | yes | yes |
| `mg` | Malagasy | yes | yes | no |

The shared list is `LOCALES = ['fr', 'mg', 'en']` with `DEFAULT_LOCALE = 'fr'` in `libs/shared-constants/src/locale.constants.ts` (type `Locale` in `libs/shared-types`). The website only serves `fr` and `en` (`apps/web/i18n/config.ts`), while content and emails can exist in the three.

## Where translations live

| App | Library | Files |
|---|---|---|
| `apps/server` | i18next (`i18next-fs-backend`, `i18next-http-middleware`) | `src/locales/{fr,en,mg}/common.json` |
| `apps/bo` | i18next + react-i18next, browser language detector | `src/config/i18n/locales/{fr,en,mg}/` (`common`, `cms`, `route`, `user`, `zod`) |
| `apps/web` | next-intl | `translations/{fr,en}/` (`app`, `article`, `common`, `form`, `zod`) |

### Server

`apps/server/src/config/i18next.ts` bundles the three `common.json` files as resources, with `fr` as the fallback and `translate(key, locale)` as the helper used by emails, validation messages and errors. The key form is `section.key` (for example `email.hi`, `error.max`). Express also gets the i18next HTTP middleware at startup. See [EMAIL_NOTIFICATIONS.md](EMAIL_NOTIFICATIONS.md) and [ERROR_HANDLING.md](ERROR_HANDLING.md).

### Back-office

- `src/config/i18n/index.ts` initializes i18next with the browser language detector, `fr` as the fallback and the `common` default namespace; the resources are assembled by `resources.ts` from each locale's `index.ts`, which names the namespaces.
- Keys are written `t('namespace:path.to.key')`.
- The `zod` namespace holds only the field names used by the Zod error messages (`zod-i18n.ts`, `zodTranslation.ts`), never interface text.
- The chosen locale is part of the persisted `settings` Redux slice and is sent as the `locale` parameter of Cloud Functions that translate server-side.
- Server errors that are keys with a namespace (`user:errors.accessDenied`) are translated by the back-office, see [ERROR_HANDLING.md](ERROR_HANDLING.md).

### Public website

- Routing is by locale prefix, always present (`localePrefix: 'always'`, default `fr`, locale detection on), declared in `i18n/routing.ts` with translated pathnames in `i18n/routes.ts`. `proxy.ts` runs the next-intl middleware.
- `i18n/request.ts` loads the five files of the locale and merges them into one messages object; components use `useTranslations('Namespace')` / `getTranslations`.
- The locale is passed to server actions as a bound argument, and then to the server (`context.locale`, `locale` parameter) so that server messages come back in the visitor's language.

## Translated content

Project, Article, Page, PageSection and Category texts are stored per locale in `translated.<locale>`. Public pages read `translated.<locale>` and fall back to the default locale when a slug is not translated (for example `getArticleForClient` matches the slug in the current locale or in the default one). Newsletter subscribers carry a `language` used to send each article in their language.

## Adding or changing a string

1. Add the key to **every** locale of the app that owns the string (`fr`, `en`, `mg` for the server and the back-office; `fr`, `en` for the website), under the same namespace and path.
2. Use the key in the code with a literal `t('namespace:key')` where possible, so the check can verify it.
3. Run `pnpm check-i18n`.

Reuse an existing `common` key before adding one, and never put interface text in the `zod` namespace.

## The check-i18n script

`pnpm check-i18n` runs `scripts/check-i18n.mjs`. It runs in the `pre-push` hook, in the `lint` script of the root `package.json`, and in the CI `verify` job. It does two checks for each of `bo`, `server` and `web`:

1. **Parity**: every key of the reference locale (`fr`) exists in each other locale of the app, and no locale has a key the reference lacks. A missing key would otherwise print the key itself or the French text in the other language.
2. **Usage** (`bo` only): every literal `t('namespace:key')` in the source resolves to an existing key and a known namespace. Keys built at runtime are skipped, and the website is not checked this way because next-intl splits the namespace from the key.

The script exits with an error listing every problem; when all is consistent it prints that translations are consistent.
