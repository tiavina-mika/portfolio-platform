## Vue d'ensemble

Il y a deux sortes de traductions : les textes d'interface de chaque app (fichiers JSON, un jeu par app) et le contenu rédigé par le propriétaire dans le back-office (stocké en base sous `translated`, voir [DOMAIN_MODEL.FR.md](DOMAIN_MODEL.FR.md)).

## Locales

| Locale | Langue | Serveur | Back-office | Site |
|---|---|---|---|---|
| `fr` | français, le défaut et la référence des contrôles | oui | oui | oui (défaut) |
| `en` | anglais | oui | oui | oui |
| `mg` | malgache | oui | oui | non |

La liste partagée est `LOCALES = ['fr', 'mg', 'en']` avec `DEFAULT_LOCALE = 'fr'` dans `libs/shared-constants/src/locale.constants.ts` (type `Locale` dans `libs/shared-types`). Le site ne sert que `fr` et `en` (`apps/web/i18n/config.ts`), alors que le contenu et les emails peuvent exister dans les trois.

## Où vivent les traductions

| App | Bibliothèque | Fichiers |
|---|---|---|
| `apps/server` | i18next (`i18next-fs-backend`, `i18next-http-middleware`) | `src/locales/{fr,en,mg}/common.json` |
| `apps/bo` | i18next + react-i18next, détecteur de langue du navigateur | `src/config/i18n/locales/{fr,en,mg}/` (`common`, `cms`, `route`, `user`, `zod`) |
| `apps/web` | next-intl | `translations/{fr,en}/` (`app`, `article`, `common`, `form`, `zod`) |

### Serveur

`apps/server/src/config/i18next.ts` regroupe les trois fichiers `common.json` comme ressources, avec `fr` en repli et `translate(key, locale)` comme aide utilisée par les emails, les messages de validation et les erreurs. La forme des clés est `section.key` (par exemple `email.hi`, `error.max`). Express reçoit aussi le middleware HTTP d'i18next au démarrage. Voir [EMAIL_NOTIFICATIONS.FR.md](EMAIL_NOTIFICATIONS.FR.md) et [ERROR_HANDLING.FR.md](ERROR_HANDLING.FR.md).

### Back-office

- `src/config/i18n/index.ts` initialise i18next avec le détecteur de langue du navigateur, `fr` en repli et le namespace par défaut `common` ; les ressources sont assemblées par `resources.ts` à partir du `index.ts` de chaque locale, qui nomme les namespaces.
- Les clés s'écrivent `t('namespace:chemin.vers.cle')`.
- Le namespace `zod` ne contient que les noms de champs utilisés par les messages d'erreur Zod (`zod-i18n.ts`, `zodTranslation.ts`), jamais de texte d'interface.
- La locale choisie fait partie du slice Redux `settings` persisté et est envoyée comme paramètre `locale` aux Cloud Functions qui traduisent côté serveur.
- Les erreurs du serveur qui sont des clés avec namespace (`user:errors.accessDenied`) sont traduites par le back-office, voir [ERROR_HANDLING.FR.md](ERROR_HANDLING.FR.md).

### Site public

- Le routage se fait par préfixe de locale, toujours présent (`localePrefix: 'always'`, défaut `fr`, détection de locale activée), déclaré dans `i18n/routing.ts` avec des chemins traduits dans `i18n/routes.ts`. `proxy.ts` exécute le middleware next-intl.
- `i18n/request.ts` charge les cinq fichiers de la locale et les fusionne en un seul objet de messages ; les composants utilisent `useTranslations('Namespace')` / `getTranslations`.
- La locale est passée aux server actions comme argument lié, puis au serveur (`context.locale`, paramètre `locale`) pour que les messages du serveur reviennent dans la langue du visiteur.

## Contenu traduit

Les textes de Project, Article, Page, PageSection et Category sont stockés par locale dans `translated.<locale>`. Les pages publiques lisent `translated.<locale>` et se replient sur la locale par défaut quand un slug n'est pas traduit (par exemple `getArticleForClient` cherche le slug dans la locale courante ou dans celle par défaut). Les abonnés à la newsletter portent un `language` utilisé pour envoyer chaque article dans leur langue.

## Ajouter ou modifier un texte

1. Ajouter la clé à **chaque** locale de l'app propriétaire du texte (`fr`, `en`, `mg` pour le serveur et le back-office ; `fr`, `en` pour le site), sous le même namespace et le même chemin.
2. Utiliser la clé dans le code avec un `t('namespace:key')` littéral quand c'est possible, pour que le contrôle puisse la vérifier.
3. Lancer `pnpm check-i18n`.

Réutiliser une clé `common` existante avant d'en ajouter une, et ne jamais mettre de texte d'interface dans le namespace `zod`.

## Le script check-i18n

`pnpm check-i18n` exécute `scripts/check-i18n.mjs`. Il tourne dans le hook `pre-push`, dans le script `lint` du `package.json` racine et dans le job CI `verify`. Il fait deux contrôles pour chacune des apps `bo`, `server` et `web` :

1. **Parité** : chaque clé de la locale de référence (`fr`) existe dans chaque autre locale de l'app, et aucune locale n'a une clé absente de la référence. Sans cela, une clé manquante afficherait la clé elle-même ou le texte français dans l'autre langue.
2. **Usage** (`bo` uniquement) : chaque `t('namespace:key')` littéral du code correspond à une clé et un namespace existants. Les clés construites à l'exécution sont ignorées, et le site n'est pas contrôlé ainsi car next-intl sépare le namespace de la clé.

Le script se termine en erreur en listant chaque problème ; quand tout est cohérent, il indique que les traductions sont cohérentes.
